# Read the e2e run's own summary artifact instead of trusting a green claim

## Context

The end-to-end suite drives the whole release pipeline inside a container. Its result reaches a reviewer as a claim — "all phases pass" — from whoever ran it. The run also writes its own verdict down, machine-readable, before it exits. The claim and the artifact are different objects, and only one of them is evidence.

## Guidance

Read the run's artifact. Each run writes a summary under its artifact root (`e2e/.artifacts/<timestamp>/`, printed by the run itself) beside a full command transcript and a machine-readable command log. The summary carries `phases[]` — name, status and duration per phase — and `failed` — the failing phase name, or `null`:

```bash
jq -r '.failed, (.phases[] | select(.status != "passed") | .name)'  <artifact>/summary.json
jq -e '.failed == null and ([.phases[] | select(.status != "passed")] | length == 0)' <artifact>/summary.json
```

The second command is the machine-readable form of "green": it exits 0 only when every phase passed. Against the newest artifact of this session's run it printed `true` (14 phases, `failed: null`); against a run with a failing phase it prints `false` and exits 1, and `.failed` names the phase.

## Why This Matters

A green claim is a statement about an artifact; the artifact costs one read, is written by the run rather than by the claimant, and cannot drift from what the container did. When the run failed, the same file names the failing phase and the transcript holds that phase's commands with their exit codes — so the verdict and its counter-evidence live together.

The general rule: whenever the producer of the work also reports the result, the report is not the verification. The artifact the producer emitted is, because it is generated by the run rather than authored by the reporter.

## When to Apply

- Verifying a delegated "the e2e passed" before reporting a change as verified.
- Deciding whether a change broke the pipeline, before requesting a re-run.
- Diagnosing a failure: read `failed` for the phase, then that phase's commands in the transcript.

## Examples

- Green: the `jq -e` gate prints `true` and exits 0.
- Red: the same gate prints `false`, exits 1, and `.failed` names the phase that failed.
- The artifact root is gitignored: the artifact exists only on the machine that ran the suite, so read it there rather than looking for it in the checkout.
- A failed run keeps its container alive and additionally writes a state snapshot (git log, tags, versions, captured files, registry and emulated GitHub state at the end) plus the fixture tarball. `E2E_KEEP=1` keeps a passing world too; under CI the keep-on-failure behaviour is suppressed, so the artifact is the only record.
- `E2E_FILTER=<substring>` re-runs only the phases whose name contains the substring. The run prints the re-attach command for a kept container.
